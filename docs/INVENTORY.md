# Inventory and Items

Phase 20 introduces Cubic's first version-aware inventory implementation. It passed controlled localhost manual acceptance against vanilla Java 26.1.2. Creative inventory and containers, Search focus/names, component-aware patterned banner transfer/placement/rendering, ordinary item lighting, beds and bounce, chests, shulkers, conduit, decorated pots, skulls, copper-golem static poses, and the collision/selection sweep were accepted. It targets Java 26.1.2 for current wire compatibility while keeping generic state independent of numeric item, component, menu, and packet IDs.

Cosmetic animations such as banner waving, chest lids, shulker opening/lids, decorated-pot wobble, and conduit animation remain deferred. Middle-mouse Pick Block is deferred to later input/keybind work rather than being a Phase 20 blocker.

## Data flow

```text
generated GameData registries
  -> protocol-775 ItemStack/container codec
  -> stable cubic-world InventoryState
  -> bounded network snapshot/action handoff
  -> replaceable cubic-ui inventory overlay
```

`InventoryState` owns the 46-slot player container, selected hotbar slot, armor, offhand, cursor stack, optional open server container, state IDs, data properties, and bounded quick-craft gesture. Open-menu updates mirror the current protocol's trailing 36 player slots into the authoritative player main inventory/hotbar. The UI and network predictor run the same deterministic click operation immediately, including the cursor stack, before the packet is sent. Server full-content and slot updates still replace that predicted state on confirmation or disagreement; close, reset, and disconnect clear transient state.

## Interaction

The functional overlay supports left/right pickup, Shift quick move, number-key swap, Q/Ctrl-Q drop, primary/secondary drag quick craft, double-click pickup-all, and middle-click Creative clone. Quick move is menu-aware: player equipment/main/hotbar, chest, furnace, and crafting-table ranges use their own destination order instead of one generic partition. Pickup-all uses exact item-plus-component equality, left-button initiation, output-slot restrictions, the current carried maximum, and vanilla's partial-stack-then-full-stack passes. Quick craft uses the protocol's start/add-slot/end sequence, filters incompatible and full destinations, respects stack capacity, and is cancelled by authoritative state changes. While the button remains held, a non-committing clone of the same menu model previews every prospective slot count and the cursor remainder; release commits the locally predicted result. `E` toggles the player inventory; server menus open from their server-provided title and close explicitly.

An authoritative Creative game mode makes `E` open the 195×136 Creative screen rather than the Survival crafting screen. Its 5×9 picker consumes the exact ordered, component-bearing 26.1.2 stacks from `cubic-version`; it never infers category membership from registry order, tags, or identifier words. The generated profile retains every tab's row, column, title key, icon stack, background, type, alignment/title/scroll/display flags, feature requirements, permission variant, Search visibility, and canonical Search result. Top/bottom selected and unselected runtime sprites use vanilla's 27-pixel tab spacing and right alignment. Titles are localized from the runtime language resource and tabs remain icon buttons with tooltips.

The ordinary Creative screen's bottom row directly presents player slots 36–44, and every edit immediately updates the same authoritative hotbar used in-world before sending protocol 775's full-stack Set Creative Mode Slot packet. Its QUICK_MOVE action follows `ItemPickerMenu`: it clears the selected real hotbar slot rather than moving into hidden inventory. The Inventory tab retains wrapped `InventoryMenu` semantics, delegates armor/offhand empty icons to the exact runtime slot sprites, and keeps its own quick-move behavior. Tab changes clear drag state but preserve the carried stack, and tab clicks are consumed before outside-drop handling. A primary click on an actual empty picker cell clears only the carried template stack. Picker stacks retain their verified carried-stack state table. Search remains bounded to 50 characters, and its focused editor consumes printable inventory-binding keys before platform-global `E` handling. Unqualified queries use a bounded lowercase index of the normal Creative tooltip projection (display name plus non-empty tooltip lines), so multi-word and component-derived names are searchable without rewriting spaces as identifier separators. Queries containing `:` use the separate namespace/path identifier search. Both paths filter the canonical Search-tab sequence without reordering it. Ordinary scrollable tabs normalize line and physical-pixel wheel events into logical steps, retain fractional X/Y remainders, clear a remainder on direction reversal, and move one nine-item row per emitted vertical step even over normal hovered items; wheel and scrollbar share one bounded row index. `#tag` search remains unavailable because Phase 11 lacks item-tag membership. Operator Utilities retains its ability/permission/option gates. Persisted vanilla saved-hotbar presets are not yet implemented.

Every open inventory screen is a platform input mode: first-person capture and held gameplay controls are cleared, the system cursor drives the GUI, and camera/movement/interaction input remains suspended until the screen closes. Closing clears input again before restoring first-person capture, so keys held during GUI use cannot leak into movement.

Clicks use container and state IDs and retain deterministic local slot/cursor prediction. The protocol boundary supplies exact hashed-stack reconciliation values where it can reproduce the current registry-aware dynamic hash; complex component types without a generated dynamic codec use an empty server-authoritative fingerprint rather than a fabricated hash. Authoritative updates then confirm or correct the prediction.

## Item appearance and gameplay integration

The network stack is a component patch, not a complete component set. Cubic therefore resolves the effective `minecraft:item_model` from an explicit added/removed patch and otherwise uses the registered item's same-named default. The renderer follows that identity through the exact-version `assets/minecraft/items/*.json` graph and inherited block/item model graph. It recognizes vanilla's non-file model-bakery roots and the current item graph forms. Flat generated layers remain ordered composites; baked GUI geometry uses resolved quads, UVs, inherited textures, GUI transforms, GUI lighting, and per-fragment depth. Completed states are packed deterministically into separate guttered atlases for GUI scales 1–4. Cells are rasterized directly at 16, 32, 48, or 64 physical pixels with matching depth buffers while remaining 16 logical GUI units; the UI selects the current scale atlas and uses nearest sampling without enlarging a 16-pixel intermediate.

The verified-cache audit covers all 1,506 registered items and records the selected renderer class rather than counting a generic substitute as success. Ordinary baked models use actual quads, generated items use actual layers, and item-used special families route explicitly through banner, bed, chest, conduit, copper-golem statue, decorated-pot, head/player-head, shield, and shulker-box static renderers; trident selects its ordinary GUI model. Special renderers use independently reimplemented 26.1.2 model-part cuboids/planes, entity-texture UV unfolding, family texture dimensions, and the transformation inherited from their item-model graph rather than generic family extents. Bed head/foot layers retain their independently transformed leg geometry; decorated pots include the four side planes omitted by vanilla's GUI-extents helper; skull items use skull-only models; and shulker/statue item transforms remain separate from their world block-entity transforms so each is applied once. Family geometry and selected runtime entity/block-entity textures feed the same physical-resolution atlases instead of particle/base-texture fallbacks. `ITEMS_3D` shading transforms baked normals through the model/item normal transforms and the exact outer GUI-atlas Y inversion before applying the two fixed vanilla light vectors; this prevents the default cube top from being inverted into the dark hemisphere. Ominous Banner's exact generated `item_name` translation is projected ahead of the base White Banner name while preserving its component bytes. Patterned inventory and placed banners now share bounded ordered static pattern composition; shield pattern composition, pot sherd face selection, animated parts, and live profile skins remain bounded dynamic-special limitations.

The same verified runtime source supplies the 26.1.2 player-inventory, row-dependent chest, furnace, crafting-table, hotbar, selection, progress, empty armor/offhand slot, slot-highlight, English localization, and ASCII bitmap-font resources. Cubic uses native GUI-pixel geometry, Minecraft-style automatic GUI scaling, exact supported-screen label coordinates/colors, and the server-provided menu title (localized when it is a known translation key). Supported screens retain exact slot coordinates, the complete player inventory/hotbar tail, stack counts with shadow, exposed durability bars, and the cursor-carried stack. The player screen deliberately omits the generic `container.inventory` label as vanilla does; chest, furnace, and crafting screens retain it. Unknown menu identities use an explicit bounded fallback rather than borrowing a misleading known layout.

The selected stable item identity feeds the existing interaction controller, while authoritative player slot 45 supplies offhand identity. Use packets carry the selected main/offhand protocol value; Cubic gives a known-consuming safe main-hand placement priority and otherwise permits a present offhand to act without emitting a duplicate speculative use. This supports offhand air use, block use, food/use handled by the server, and safe offhand property-free block placement. Full client-side simulation of every item's consumption result remains deferred, so unknown dynamic actions remain server-authoritative.

Normal Play accepts number keys and the vanilla fractional mouse-wheel accumulator. Vertical scroll wins over horizontal scroll, direction changes clear the old fractional remainder, selection wraps across slots 0–8, and the local selection marker updates immediately before the existing selected-slot command is sent. Open inventory/container screens consume wheel input as GUI input and never change the gameplay hotbar.

The isolated 26.1.2 adapter applies basic material tool speeds for currently modeled blocks and preserves empty-hand behavior. Enchantments, effects, and exhaustive generated tool tags are not modeled. Placement prediction is restricted to generated property-free item-to-block mappings into known loaded air; directional or otherwise stateful placement remains server-authoritative.

Furnace routing recognizes the common current-version fuel and smeltable families available from Phase 20's existing stable item identity. Exhaustive recipe/tag-driven furnace eligibility waits for generated recipe/tag data rather than guessing server recipes. Creative category membership/order and operator permission content are exact generated version data. Item-tag text search, persisted saved-hotbar presets, and remaining niche Creative gesture parity remain explicit follow-up fidelity items within Phase 20 acceptance.

The current fidelity pass applies inherited item-graph translation/quaternion/scale transformations before the inherited-or-overridden GUI display transform in vanilla order: center pivot, scale, JOML `rotationXYZ`, model-unit translation, then GUI projection. Per-fragment depth resolves overlapping block-item faces. `minecraft:select` can read a named value from the effective stack's bounded `minecraft:block_state` component, so Light levels 0–15 and Test Block start/log/fail/accept select distinct resource models and atlas identities. Models using block light use the verified 26.1.2 ITEMS_3D two-direction normal formula (`min(1, (max(dot(L0,N),0)+max(dot(L1,N),0))*0.6+0.4)`); front-lit generated items remain flat. Creative tabs use three explicit paint layers so inactive tabs sit behind the panel and the selected tab overlaps it. Real Creative player slots mirror cursor state into the network-owned inventory model before slot edits, preventing a carried stack from being erased by the next authoritative snapshot.

Named special renderers now share one Minecraft-style ModelPart baker between inventory and world rendering. It preserves hierarchical pivot/XYZ pose composition, per-part visibility, cube deformation and face masks, entity cube-net UVs, zero-thickness planes, and winding under negative-determinant transforms. Beds retain separate transformed head and foot nodes; banners retain pole/bar/flag parts; chests retain base/lid/latch geometry and joined variants; shulkers use direction-specific world transforms without reapplying their item transform; pots submit the exact neck, zero-height top/bottom cubes, and four one-sided planes; zombie skulls use the 64×64 head-plus-hat-only layer; and piglin ears remain child-local around their exact pivots. Inventory copper-golem icons retain their accepted item path while placed statues select the exact Standing, Running, Sitting, or Star hierarchy, apply the model root pose once, and then apply only the placed facing transform. For placed special families the ordinary terrain fallback geometry is replaced by the same shared static model, while collision/environment semantics remain authoritative. Block-entity payload summaries expose ordered banner patterns from both chunk data and live updates; player-skin profiles, pot sherd identity, and animation state remain bounded static defaults rather than being guessed.

Normal non-empty-slot hover tooltips use the verified runtime tooltip background/frame, localization, and bitmap font. They project bounded custom/item names and lore while retaining the exact original component bytes for protocol round trips; the Search tab may add the canonical Creative category. Styled, translated, and interactive component parity remains Phase 25 work.

The shared entity-style cube baker now follows the exact 26.1.2 `ModelPart.Cube` directional polygon construction rather than reusing block-model face conventions. Its oracle pins vertex selection, cube-net rectangles, Polygon UV remapping, authored normals, mirror behavior, winding, and zero-sized planes for all six directions. Canonical component-bearing banner stacks also receive distinct atlas keys; bounded ordered `BANNER_PATTERNS` layers are parsed without a registry dependency, referenced Holder IDs are decoded from their raw-ID-plus-one wire form, and rendering resolves at most vanilla's first 16 pattern layers against the exact numeric built-in registry order captured with the Creative artifact. A missing registry is a bounded deferred lifecycle state, while an available registry with an invalid holder ID remains a malformed-data error. Server-provided stacks use their Configuration registry rather than assuming the built-in ordering. The protocol codec additionally retains and re-encodes direct Holder values. Placed-banner block entities decode persistent `patterns` list entries as referenced identifier or direct `{asset_id, translation_key}` holders plus dye name; their base dye remains block-state-owned. Static world flags reuse the inventory compositor, and live updates revision/remesh the affected chunk.

The language loader applies the exact-version `assets/minecraft/lang/deprecated.json` removals and renames to `en_us.json` before constructing UI, tooltip, and Creative Search translations. This preserves runtime names such as Flower Charge, Creeper Charge, Skull Charge, Thing, Globe, Snout, Flow, Guster, Field Masoned, and Bordure Indented Banner Pattern without identifier-derived special cases. Search renders its selected-tab title and borderless editor together at their vanilla panel coordinates.

The 26.1.2 shulker menu uses the ordinary three-row generic-container screen: 27 container slots followed by the 36 player slots over the runtime `generic_54` background. Bed contact uses the verified living-entity rebound factor and suppresses rebound while sneaking. A generated shape oracle covers all 29,873 registered block states separately for collision and selection; the 29,828 state-static collision entries and all outline entries have zero adapter mismatches. Scaffolding, powder snow, and moving pistons remain explicitly tagged as collision-context families rather than being represented as universally static facts.

## Bounds and deferred work

Placed banner patterns now use a dedicated GPU banner-pattern atlas/material (`minecraft:textures/atlas/banner_patterns.png`) with the same `entity/banner/<asset_id>` sprite identity as inventory icons. World meshing requires an exact atlas region for each pattern instead of silently using the terrain missing-texture placeholder; late block-entity updates still revision/remesh the affected chunk. Creative Search automatically focuses its editor on tab selection, keeps keyboard entry available after slot clicks, and clears/releases focus when leaving the tab. Middle-mouse Pick Block is deferred to later unified desktop/iPad controls work, including configurable binding and Creative clone/pick semantics; it is not part of this Phase 20 corrective pass.

The Creative picker carries a template locally without sending a container packet; only a real inventory/hotbar slot edit emits one `minecraft:set_creative_mode_slot` packet. Its serverbound untrusted ItemStack codec length-delimits every added component value, unlike the clientbound inventory codec. A development-only official 26.1.2 packet oracle established the canonical Ominous Banner's first added value as component type `72`, length `17`, followed by its eight ordered pattern layers. Static Creative templates retain their original bounded registry order alongside those bytes; the versioned profile first resolves semantic pattern keys in that source order, then encodes references through Configuration's connection-owned `minecraft:banner_pattern` ordering. Clientbound inventory stacks already use the connection mapping. The WorldState `runtime_registries=0` summary does not describe the inventory protocol profile. DEBUG inventory diagnostics report packet/slot, component IDs and encoded lengths, and bounded banner holder/dye metadata without logging component contents.

Slot/component/action/model-graph and atlas limits are documented in `SECURITY.md`. Phase 20 intentionally does not add recipes or recipe-book behavior, inventory-driven crafting simulation, the player model preview, item entities, dropped-item rendering, held-item first-person rendering, complete dynamic special-component composition, cooldown state, foil animation, arbitrary formatted-title parity, or complete styled/interactive tooltips. Those presentation limitations remain explicit. Phase 21 entities and Phase 25 complete text/tooltip semantics remain unstarted. Automated tests never perform network access.
