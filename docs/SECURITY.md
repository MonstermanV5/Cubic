# Security Principles

Cubic will process hostile or malformed data. All network input, server data, resource packs, downloaded metadata, and archives must be treated as untrusted.

- Validate lengths and enforce bounded allocations before reserving or reading externally specified sizes.
- Parsers must return structured errors for malformed input rather than panic.
- Prevent archive and path traversal by validating paths and extraction destinations.
- Apply compressed-size, expanded-size, nesting, and resource limits to defend against decompression bombs.
- Never log credentials, passwords, access tokens, refresh tokens, private keys, or signing material.
- Use platform-appropriate secure credential storage when authentication is implemented later.
- Verify Mojang-provided resource hashes before accepting resources when resource downloading is implemented later.
- Never download or execute arbitrary executable code.
- Treat resource packs as untrusted data, not trusted code.

Phase 3's protocol reader uses checked slice access and borrowed results where ownership is unnecessary. Length-prefixed strings, byte arrays, BitSets, frame bodies, and aggregate fragmented input are bounded before allocation or copying. Fallible reservation reports a structured error. Incremental framing never trusts a declared frame size and does not allocate the frame body until all bounded bytes are present. Malformed or truncated data returns `CodecError`; production decode paths contain no unsafe code or intentional panic path.

Phase 4 NBT decoding carries one resource context through the entire nested document. It enforces depth, total-tag, per-compound, per-list, per-array, per-string, and cumulative allocation/resource limits. Array byte sizes and structural budget additions use checked arithmetic. Declared array bytes must be present before output storage is reserved. Modified UTF-8 is decoded into bounded UTF-16 storage without silently repairing unpaired surrogates. Production NBT parsing uses no unsafe code, unchecked external indexing, or panic-based error handling.

Phase 5 treats DNS results, TCP bytes, frames, JSON, MOTD components, player samples, favicons, and unknown server fields as untrusted. The query has separate connect and per-operation I/O timeouts plus an overall deadline. Status frames are limited to 128 KiB and the incremental receive buffer to 256 KiB. The JSON string, player sample, individual text fields, and favicon text have additional bounds. Lengths are validated by `cubic-protocol` before body ownership or JSON parsing. Pong packet ID, shape, and nonce are validated. Server-supplied text is displayed as text; favicon content is retained but not decoded, interpreted, fetched, or rendered. Cubic does not follow URLs or execute content supplied by a Status response.

Limits are explicit inputs to codecs so future packet schemas can apply field-appropriate bounds. The default frame body limit is the current protocol maximum of 2,097,151 bytes, while aggregate buffered input has a separate 8 MiB default. Callers may configure stricter bounds. These protections do not replace future per-connection budgets, timeouts, decompression limits, or transport backpressure.

Phase 6 version-data loading treats all filesystem input as untrusted. Version IDs are validated as opaque strings before use as filesystem path components: empty, dot, double-dot, path-separator, control-character, Windows-reserved-name, filesystem-reserved-character, and overlong values are all rejected with structured errors before any path is constructed. Symbolic links are rejected at the root, versions directory, individual dataset directories, and individual files. File sizes are bounded (64 KiB per version dataset, 1 MiB for the catalog) before content is read; a secondary bounded `Read::take` guard prevents racing filesystem size changes from bypassing the initial check. JSON parsing uses `serde_json` with `deny_unknown_fields` on wire types. The format version is validated before typed payload deserialization. The catalog is cross-validated against every installed dataset on open. `cubic-version` performs no network access, no subprocess execution, and no dynamic code loading. The `version-generator` tool is an offline-only utility that operates on local files; it also contacts no network.

Phase 7 continues to treat even a local development server as untrusted. A single incremental decoder applies independent frame and aggregate-buffer caps across arbitrary TCP fragmentation. Login properties, usernames, custom payloads, Known Packs, disconnect data, configuration packet counts, and displayed error previews have explicit bounds. Each operation and the overall sequence have deadlines. Packet handlers reject state-inappropriate IDs, malformed/trailing fields, EOF, and unsupported features with structured errors. Encryption and compression are not partially interpreted: their negotiation packets stop the connection and explain the required local server setting. Server-supplied text remains inert and is never executed, fetched, or logged without truncation. Production Phase 7 input paths use no unsafe code, unchecked indexing, panic, `unwrap`, or `expect`.

Phase 8 preserves the framing caps and adds independent resource bounds: chat input is at most 256 Java UTF-16 units, retained UI history is at most 500 messages and 256 KiB of projected text, the regular event queue is 128 entries, the outgoing queue is 16 entries, text components are bounded by the packet/frame and a 32 KiB component policy, last-seen chat entries are capped at 20, and ignored world frames are never queued or retained. Queue overflow is counted and displayed; terminal disconnect state has a separate bounded slot. Rich text is inert data: click and hover actions are neither followed nor executed. Windows CJK fallback loading considers only a fixed list of installed OS font filenames and bounds the selected file to 64 MiB before passing it to egui. Font loading occurs once during platform startup, never from the render loop. No blocking I/O runs during UI rendering, and idle Chat Mode does not continuously submit frames.

Phase 9 treats Microsoft/Xbox/Minecraft tokens, OAuth authorization codes, PKCE verifiers, XAL device keys/identifiers, player private keys, and Minecraft AES secrets as sensitive. Owned secret strings are redacted from formatting and zeroized on drop. Cubic is a public native client: it uses Authorization Code + S256 PKCE, accepts no Microsoft password, has no client secret, and must never borrow another independent launcher's client ID. Cubic-Entra uses the system browser; experimental XAL uses an isolated Windows WebView2 navigation host because its fixed desktop redirect cannot reach Cubic's loopback listener. The host runs privately, observes only top-level URLs, restricts those URLs to reviewed exact Microsoft identity hosts over HTTPS, rejects misleading hosts/ports/user information, captures only the exact state-validated callback, and disables downloads, permissions, popups, developer tools, general autofill, and browser persistence. It does not inject scripts or inspect DOM/form/keyboard data. Windows refresh credentials and the experimental XAL P-256 device identity use separate Credential Manager records with no plaintext fallback; unavailable platforms fail explicitly. Authentication HTTP uses compiled HTTPS origins, finite timeouts, disabled redirects, bounded bodies, and normal TLS validation. XAL proof-of-possession requests use a fresh or securely restored P-256 key and the documented signed-message layout; TLS validation is never weakened. Compressed Minecraft packets enforce declared-size and output bounds against decompression bombs.

Player-certificate responses are bounded to 256 KiB, parsed strictly, and must contain a matching RSA-2048 PKCS#8 private key and X.509/SPKI public key, a bounded Mojang signature, valid timestamps, and an unexpired lifetime. The decoded private-key bytes use a zeroizing temporary buffer; the parsed signing key is memory-only, redacted from formatting, never logged, and never written to credential storage. The implementation uses the audited `rsa` crate's SHA-256/PKCS#1 v1.5 primitive rather than custom cryptography. Signed-message and acknowledgement histories are fixed-capacity.

Only Status, the protocol-775 bootstrap profiles, Phase 8's narrow Chat Mode Play subset, and Phase 9's authenticated Login/secure Chat foundation are implemented. Incoming player-chat signatures are classified and tracked but are not yet cryptographically verified because Cubic deliberately does not parse/retain the world/player-info key graph in this phase. Rendering performs no network operations. See `AUTHENTICATION.md`.
