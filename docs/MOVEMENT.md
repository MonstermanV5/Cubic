# Phase 17 movement and collision

Phase 17 adds the first locally predicted player controller to the separate offline-development World Mode. Its basic movement/collision framework passed localhost acceptance and is deliberately independent of render FPS and Chat Mode. Comprehensive vanilla block collision-shape fidelity and sneak-edge prevention were split into Phase 17B without changing the accepted movement equations.

## Ownership and timing

`cubic-platform` translates Windows W/A/S/D, Space, left Shift, left Control, and relative mouse motion into sequenced semantic `MovementInput` and sequenced cumulative look totals. A latest-value mailbox coalesces held input; it is cleared on focus loss, Escape, and shutdown. Clicking World Mode captures and hides the cursor, while Escape or focus loss releases it. Space is persistent level state: every fixed tick sees its current value, so holding it through landing launches again on the landing tick while releasing it before that tick prevents the jump.

Winit records held input immediately, assigns a monotonically increasing source sequence, and appends changed snapshots to a bounded 64-entry transition journal. The newest sequenced held state is authoritative: a stale aggregate snapshot cannot overwrite a newer release, and journal eviction cannot leave a key permanently latched. The journal preserves ordered protocol-visible edges while deterministic oldest-transition eviction remains a counted safety valve. Focus loss records a sequenced all-released state. The persistent `cubic-network` task owns a 20 Hz Tokio interval with missed ticks set to `Skip`, so a stall cannot create an unbounded catch-up loop. Each tick consumes the retained state/transitions, advances the `cubic-world` simulation from the final held state, publishes its local predicted pose to the render mailbox, emits ordered Player Input transitions, and terminates with Client Tick End. Short taps entirely between physics ticks produce no displacement, but their wire/input edges are no longer silently collapsed.

Protocol-775 Level Chunk With Light decoding is classified in the version profile and moved to a bounded blocking worker one packet at a time. While that decode is pending, the same 20 Hz movement service continues to run. Network-to-render publication now clones an immutable `Arc<Chunk>` rather than deep-cloning every decoded section; live mutation uses copy-on-write so an in-flight render revision remains immutable. The mailbox contains only the newest delta for each coordinate, and the renderer swaps its pending map under the lock before doing allocation or scheduling. A renderer which consumes nothing therefore makes terrain late but cannot backpressure semantic world mutation or movement. Superseded render revisions remain disposable; authoritative `WorldState` is not.

The remaining real 80-375 ms "publication" timings were traced to the old measurement enclosing a per-chunk DEBUG record: the tracing writer synchronously took one global file mutex and wrote both disk and stderr on the network/movement task. Diagnostics now enter a bounded lossy background writer (8,192 lines), and verbose per-chunk records are TRACE-only. Mesh workers still perform CPU meshing and create GPU vertex/index buffers through a cloned thread-safe wgpu device. Foreground preparation shares one four-millisecond deadline across result integration and at most eight new dispatches; progress accounting and camera upload are timed separately. This fixes the old `integrated=0` loophole, where unbudgeted dirty scheduling and synchronous progress output could exceed 50 ms. Slow-path records now include mailbox lock/bookkeeping and prepare-stage breakdowns without doing their I/O on latency-sensitive threads.

Mouse presentation uses persistent display-rate yaw/pitch owned by the renderer. Every accepted raw mouse event updates that orientation immediately, in order, with Minecraft yaw wrapping and per-event pitch clamping. The 20 Hz simulation independently samples the latest absolute intended orientation for physics and wire packets; an ordinary simulation sample or acknowledgement never replaces the already-presented camera orientation. Keyboard snapshots have a distinct source sequence and cannot acknowledge, replace, or alter mouse state. A deterministic mixed-input matrix covers held and rapidly changing W/A/D, sprint, sneak, jump, and creative-flight controls, while straight, reversal, circle, tight-circle, and figure-eight traces compare every displayed step with direct raw-event integration. This remains constant-size and cannot build an input queue.

The former `simulated rotation + (produced totals - acknowledged totals)` formula conserved endpoint totals and was exact for ordinary unconstrained yaw/pitch, including normal sign reversals. It was not a sound owner for temporal presentation at the nonlinear pitch boundary: multiple clamp-crossing reversals between adjacent 20 Hz samples could differ from per-event integration by several degrees. Persistent display orientation removes that reconstruction entirely. Initial poses and authoritative server rotations/corrections explicitly rebase display and simulation state; input sequenced after the authoritative sample remains applied once, while older pending simulation delta is discarded.

An earlier renderer hardening remains in place: mesh dispatch respects the foreground deadline before its first attempt and short-circuits at known worker capacity. The follow-up localhost trace contained no render-preparation, movement-tick, or raw-mouse slow-path diagnostic, so renderer starvation was not the cause of the remaining circular-gesture defect.

Initial and corrected server positions seed or reconcile prediction. Canonical `WorldState` continues to represent server-authoritative state rather than being overwritten every local tick. Once World Mode prediction is active, only the movement controller publishes camera pose: unrelated semantic world updates cannot republish the older authoritative position, and the render mailbox consumes pose as a delta rather than attaching it to every later chunk update. Real server corrections still update `WorldState`, reconcile the movement controller, and publish the corrected `LocalPlayerPose` through that single owner. Relative corrections are resolved against the current predicted pose, while the separate authoritative rotation baseline remains available across respawn. Respawn, reconfiguration, dimension reset, and disconnect discard local prediction and movement-packet baselines. The client pauses positional simulation until the player's current chunk is loaded, and unavailable neighboring collision data is treated conservatively rather than as noclip space.

Minecraft 26.1.2 presents local camera translation using the render partial tick: vanilla's camera linearly interpolates the entity's previous and current x/y/z and eye height for the current frame. Cubic follows that presentation rule without changing the 20 Hz simulation or its server packets. The renderer retains only the previous/current predicted pose and tick timestamp for translation and eye-height interpolation; orientation remains the persistent display-rate state. A local pose publication also sends a lightweight winit user event after releasing the mailbox lock. The event loop consumes the coalesced pose and requests a frame immediately instead of waiting for its former idle 50 ms poll; bulk chunk publication remains pull-driven and cannot flood the event queue. Standing still remains exact. A correction/teleport, reset, or newly seeded presentation rebases position and orientation explicitly, so large authoritative changes snap rather than smear through invalid space.

`CUBIC_LOG_LEVEL=debug` records state-changing key arrival/consumption and the low-frequency grounded-jump path from input sample through pose publication, render-loop observation, and first submitted frame. `CUBIC_LOG_LEVEL=trace` adds every tick, pose handoff, frame sample, mouse event/accounting step, and chunk detail for short investigations; these high-frequency records deliberately remain out of DEBUG.

## Physics and collision

The player uses f64 feet coordinates, a 0.6-wide AABB, 1.8 standing height with 1.62 eye height, and 1.5 crouching height with 1.27 eye height. The deterministic tick covers normalized camera-relative walking/strafing, stateful sprint eligibility, sneak speed changes, grounded level-sensitive jumping, gravity, vertical/horizontal drag, block slipperiness, landing, walls, ceilings, corners, and a bounded 0.6-block step candidate.

Normal ground travel follows the current 26.1.2 `LivingEntity` equations verified from the installed client: input acceleration is `movement_speed * 0.21600002 / slipperiness^3`, while the separate post-move horizontal multiplier is `slipperiness * 0.91`. Airborne input acceleration is `0.02` and horizontal drag is `0.91`. Velocity is retained between ticks, so walking and sprinting build progressively and releasing input decelerates rather than stopping immediately. The grounded state sampled at the beginning of a tick selects those travel rules; a jump changes vertical velocity without prematurely selecting air rules for its takeoff movement. The exact downward contact probe is classified as grounded rather than being rejected by its own epsilon threshold.

An ordinary jump sets vertical velocity to at least `0.42` and adds no horizontal boost. A sprint jump additionally applies the vanilla `0.2` impulse along the player's facing direction before travel. Subsequent airborne ticks retain horizontal momentum, add only air control, and apply air drag. Consequently chained sprint jumps begin later takeoffs with retained momentum, while head collisions shorten the airborne cycle without zeroing horizontal velocity. These are equation-driven effects rather than distance-specific boosts.

Minecraft 26.1.2 starts ground sprint only with positive forward impulse; forward plus strafe qualifies, while pure lateral or backward input does not. Once active, sprint persists after the physical sprint key is released while forward input remains, stops when forward impulse is lost, and survives an ordinary jump. Crouching prevents a new sprint but, matching the current client state machine, does not by itself clear an already active sprint; sneaking still applies its movement slowdown. Cubic conservatively cancels on any horizontal collision because Phase 17 does not yet model vanilla's finer `minorHorizontalCollision` distinction. The raw Player Input sprint bit remains the physical key state, while Player Command start/stop transitions and the local speed multiplier use the resolved sprint state.

Collision is semantic and owned by `cubic-world`; it never uses render-model geometry. A startup `BlockCollisionProfile` is derived once from the validated exact-version Phase 11 block IDs, identifiers, and state properties. It has explicit empty, full-cube, and bounded multi-AABB shapes, with ordinary slabs, snow layers, carpets, and straight stair geometry supported. Unknown states use a full-cube fallback. Lookups perform no JSON, archive, filesystem, or GPU work during ticks, and the broadphase is capped at 4,096 block cells.

The first localhost acceptance exposed a floating-point boundary defect: a server correction to a mathematically exact `0.3` player-radius boundary can represent the AABB edge infinitesimally inside the neighboring integer block plane. Exact collision-side comparisons then failed to recognize the approach side and allowed the next local tick to re-enter the block, producing repeated server corrections. Axis overlap and approach comparisons now use the same small explicit collision tolerance, including negative coordinates, while resolved motion targets the legal plane instead of adding a large offset. Synthetic regression coverage reproduces 20 correction-triggering re-entries with the former comparison and zero with the corrected resolver.

Correction-only DEBUG diagnostics retain bounded context: teleport ID and relative flags, pre-correction prediction and velocity, authoritative position and delta, resulting velocity, grounded/collision flags, last movement family and sent position, the player AABB, at most 24 nearby semantic collision candidates, approximate-shape markers, and aggregate correction/burst/approximate-collision counters. The first movement family emitted after each correction is logged separately. These diagnostics are not emitted every tick.

Phase 17 deliberately stops short of a comprehensive vanilla collision-shape generator. Common vanilla doors use property-driven 3/16-thick planes for all four facings, open/closed states, hinges, and both halves. Empty, partial, multipart, state-dependent, and neighbour-dependent physical shape fidelity plus sneak-edge prevention are assigned to Phase 17B. Climbable/fluid physics, swimming/crawling, attributes/effects/enchantments, vehicles, elytra, and other special movement mechanics remain deferred beyond that collision milestone. Shapes not covered by an explicit Phase 17 rule are marked approximate for correction diagnostics. Cubic does not derive collision from visual models or silently treat unknown states as air.

Jump input is level-sensitive while grounded: tapping Space performs one jump, while holding Space permits another ordinary jump only after landing. It does not repeatedly add jump velocity while airborne. This also remains correct after a correction temporarily invalidates the local grounded state.

Creative flight follows the current vanilla 26.1.2 client state machine. A server-provided `may_fly` capability gates a seven-tick (350 ms) double-Space gesture. The gesture consumes timestamped raw press edges rather than 20 Hz held snapshots, holding Space cannot retrigger it, focus loss clears a partial gesture, and transition-journal overflow cancels rather than invents a toggle. While flying, collision remains enabled, Shift descends instead of selecting the sneak pose, Space ascends, horizontal input remains normalized, the server-supplied base flight speed is doubled while sprinting, vertical input is three times that speed, and vertical velocity damps by 0.6. Gravity is disabled until flight is toggled off; touching ground disables flight and reports that state to the server. A clientbound capability revocation immediately overrides local flight. Respawn/reset clears active flight and partial gesture state while retaining no locally invented permission.

## Protocol 775 boundary

The versioned 26.1.2 bootstrap profile owns every current wire value. Phase 12 packet-schema cross-checks and read-only inspection of the official 26.1.2 classes established:

- Move Player Pos `0x1e`: x/y/z f64 plus one flags byte;
- Move Player Pos Rot `0x1f`: x/y/z f64, yaw/pitch f32, flags;
- Move Player Rot `0x20`: yaw/pitch f32 plus flags;
- Move Player Status Only `0x21`: flags only;
- Player Command `0x2a`: entity VarInt, action VarInt, data VarInt;
- Player Input `0x2b`: one bit field for forward/back/left/right/jump/sneak/sprint;
- serverbound Player Abilities `0x28`: one flags byte, with only flying bit `0x02` used;
- clientbound Player Abilities `0x40`: capability flags followed by big-endian flying/walking speed f32 values;
- Client Tick End `0x0d`: an empty packet sent after the current tick's movement/input updates;
- clientbound Player Position `0x48`, Player Rotation `0x49`, and Set Entity Motion `0x65`.

Movement flags are bit 0 on-ground and bit 1 horizontal collision. Current-version sneaking is the Player Input bit, not a legacy entity-action command. Sprint transitions additionally use Player Command action ordinals 1/2 and are not repeated each tick. Position packets use the vanilla 4e-8 squared-delta threshold, exact rotation change detection, flags-only updates, and a forced positional update after 20 ticks. Normal walking never emits teleport packets.

Current Set Entity Motion uses Minecraft's variable-length `LpVec3` codec rather than the historical three signed shorts. Player Position carries both transform-relative bits and delta-velocity-relative bits; the latter preserve/replace velocity component-wise and can rotate the prior velocity using the correction's rotation delta. Only motion for the local entity enters prediction.

## Acceptance status

Automated tests use synthetic chunks and mock/pure packet vectors only; they never contact a server. Localhost retesting accepted exact-pole camera stability, stair transforms, door rendering/collision, live remote block updates, creative flight, and the final corrected movement feel. Focused regressions cover partial-tick translation/eye presentation, correction snapping, sequenced held-state rejection of stale snapshots, release safety across journal overflow/focus loss, 10,000-event cumulative mouse rebasing, immutable copy-on-write render snapshots, a renderer which consumes no updates for 500 ms, bounded latest-revision coalescing, creative-flight physics, server capability revocation, timestamp-preserving double-Space recognition after delayed consumption, exact ground/sprint acceleration curves, release deceleration, normal versus sprint takeoff, airborne turning, chained sprint-jump momentum, low-ceiling cycles, and the non-sprint three-block-distance sanity bound. The optimized Windows release build passed manual localhost acceptance as essentially vanilla-like for the basic movement milestone. An isolated small stutter also appeared in the official client and disappeared after restarting the local server, so it is not a Phase 17 blocker. Comprehensive block collision-shape fidelity and sneak-edge prevention are Phase 17B.
